# Solar Flow｜产品需求与 Prompt 总档案

> 公开版说明：本文归纳需求 Prompt、产品决策和实现验收，不是私人聊天记录的逐字公开。发布前已删除或泛化真实账单、具体商户/机构、邮箱、本机路径、Firebase 项目标识及账户/计费状态；不包含账单原件、个人截图、账号凭证或云端用户数据。需求内容继续按产品规则保存，便于贡献者理解设计背景。

- 当前定位：个人、本地优先、离线可用的人民币记账与资金规划 PWA

## 1. 产品愿景

Solar Flow 帮助用户快速记下收入与支出、看清钱的去向，并用简单的虚拟资金分配管理生活、应急与具体计划。产品应像成熟的个人工具，而不是“AI 产品”：信息直接、界面克制、重要动作容易发现，日常记账不需要复杂开户或会计操作。

核心体验：**让钱流向生活。**

### 设计原则

1. **先清楚，再丰富**：常用信息优先；功能可多，但操作步骤和视觉噪音要少。
2. **资产口径单一**：展示一个总资产数，不把微信、支付宝、银行卡拆成钱包账户。
3. **记录与导入并行**：可即时手动记账，也可隔几天批量导入历史账单。
4. **历史可解释**：日期、去重、基准余额和导入影响都要可追溯，不能悄悄重复计入。
5. **桌面与手机同等可用**：响应式布局覆盖 iOS、Android 和电脑；离线时仍可记账。
6. **动效服务理解**：动画让数据出现、切换和反馈更自然，不得牺牲可读性、速度或可访问性。

## 2. 目标用户与边界

- 当前为个人自用；以后可能增加少量使用者，不按商业化产品设计。
- 默认且唯一币种为人民币，不需要美元模式。
- 用户明确表示无需为个人数据做展示脱敏；但真实流水仍应留在本机，不应随网页源码发布。
- 未登录时数据保存在浏览器本地；GitHub Pages 只托管应用前端。
- 用户后续恢复多设备同步诉求，方案选 Firebase Authentication 邮箱/密码与 Cloud Firestore 起步；同步要求账号隔离、邮箱验证、Firestore 安全规则、离线本机写入和联网补传。Firebase 与公网前端已经配置；登录/同步是否可用仍取决于设备网络及用户端到端验收。
- 截图/OCR 账单导入属于第二阶段；第一阶段先做好表格与流水文件导入。

## 4. 核心数据规则

### 4.1 账本隔离

- 可新建多个账本，例如“测试账本”和“日常账本”。
- 新账本从零开始，不继承其他账本的流水、总资产、资金分配、借款或导入批次。
- 账本切换只改变当前查看的数据空间；清空当前账本应可通过撤销恢复。
- 账本用于隔离测试和正式记录，不应依赖用户清空或重置浏览器来开始一套新记录。

### 4.2 总资产与余额基准

- 初始总资产为 ¥0，所有初始资金余额也为 0；用户可手动设置总资产，例如 ¥1,000 或 ¥4,000。
- 总资产是所有来源合并后的单一数字；虚拟资金分配只改变“钱放在哪里”的规划，不另造资产。
- 维护“余额基准金额 + 基准日期”。基准日之后的有效收入增加总资产、支出减少总资产；基准日前的历史流水不应误改已经结清的基准余额。
- 若导入较早流水并希望重算，应允许用户把基准日期设到待补流水之前，并提供期初余额。导入预览需明确显示本批预计资产变化及导入后总资产。
- 手动流水日期默认为当前本地日期；导入必须保留原始交易日期。延迟数日或数月导入，应按正确日期顺序更新账本，而非按导入当天处理。
- 重复导入不得重复改变总资产。

### 4.3 虚拟资金分配

资金类型以用户提供的《资金类型.txt》为依据。当前规范中的基础类型：

| 类型 | 用途 | 目标线 |
| --- | --- | --- |
| 生活资金 | 日常消费优先支出 | 不设置 |
| 其他资金 | 尚未分配的总资产余额 | 不设置，自动计算 |
| 自由资金 | 可灵活安排的资金 | 不设置 |
| 计划资金 | 面向具体未来目标的资金 | 每个计划各自可设目标 |
| 紧急资金 | 前四类不足时的最后保障 | 不设置 |

- 支出扣减顺序固定为：**生活 → 其他 → 自由 → 计划 → 紧急**。
- 用户可新增多个独立计划资金；每个计划可分别设置名称、金额、目标、封面图片和留言。
- 计划封面接受常见图片格式；封面为装饰资料，不影响金额、资产或扣减规则。
- 计划卡片本身可点击进入编辑；不再使用显眼的“编辑”按钮。
- 资金卡片金额可直接编辑；目标线只出现在各计划资金卡片上，生活、紧急、自由及其他均不显示目标线。
- 收支及导入形成的分配变化要遵循同一优先级，不能因为入口不同而出现不同算法。

### 4.4 流水

- 手动新增仅提供“支出”和“收入”；不要求用户记录转出账户，不提供繁琐的手动转账流程。
- 交易日期默认实时日期；商户/来源是可选项，允许留空。
- 支出分类包括吃喝、居住、交通、通讯、购物、娱乐、医疗、学习、人情、订阅、其他；收入分类另行呈现工资与劳务、退款与返还、红包与人情、利息与收益、其他收入等。
- 手动支出的资金扣减由规则自动完成；用户不必手选从哪个钱包/账户付款。
- 列表按日期分组：一天只显示一个日期标题，下面列出当日多笔流水。
- 支持撤销最近操作，以及清空当前账本；清空必须可撤销。

### 4.5 账单导入、去重与总资产结算

- 第一阶段至少支持微信、支付宝等常见账单表格/文本导出（XLSX、XLS、CSV；已有界面亦列出 OFX）。解析应识别表头位置、日期、金额、方向、交易对方、交易号、状态和交易说明。
- 上传后先预览，再确认导入；预览可逐行修正分类、识别待确认流水、已存在流水、与手动记录匹配项和不计收支项。
- “账单来源”仅用于区分不同导出来源及辅助去重，不得显示为微信账户、支付宝账户或银行卡账户。
- 用户可能有两个微信号、两个支付宝号。同一天同金额并不意味着是同一笔；不能只按日期合并。应结合来源标识、平台交易号、日期、金额、对方和交易信息判断重复或匹配。
- 两个本人账户之间的互转不改变总资产；账单中明确为内部转账、还款结转等非消费流水时，不应错误计为收入或支出。
- 已有手动记录与导入流水能够匹配时，应允许合并而非双计；重叠月份再次导入应去重。
- 每次导入的新增、合并、重复、待确认、分类待确认和中性流水数量应清晰展示。
- 预估资产影响和“导入后总资产”必须易见；最终“导入新记录并合并匹配项”按钮固定在预览底部，不得要求滚到全部流水末尾才能找到。
- 账单解析只在本机执行；不得把用户账单上传到公开仓库或第三方服务。

### 4.6 商户分类规则

- 分类尽量明确且可解释，并在预览中允许用户修正。
- 餐饮商户归为“吃喝”；通信服务商归为“通讯”（在用户口径中属于交通通讯类支出）。
- 学校类商户按用户指定默认归到“吃喝”，不默认归“学习”。
- 看起来像真人姓名的交易对方默认归到“吃喝”，但标记为低置信度/建议确认，避免把所有个人转账都无条件认成消费。
- 学习类不作为普通消费的优先猜测；只有交易内容明确表示课程、教材等学习服务时才分类为“学习”。
- 不确定的分类保留为可确认状态，不得静默强行归类。

### 4.7 借款与信用

- 支持记录欠款、借款、信用卡和分期余额；页面轻量，不做复杂账户/还款流程。
- 流水或账单可能已经包含还款。可明确匹配到某项负债的还款，应冲减对应余额，避免再造一笔重复支出；匹配不确定时应让用户确认，而不是错误自动划销。
- 负债余额与总资产/支出统计口径需明确分开；不能把负债余额直接当成消费，也不能把内部还款重复计入支出。
- 提供简单的已还清/划销操作，并支持撤销。

## 5. 页面功能与分析

### 5.1 总览

- 首屏优先显示总资产、当期收入、当期支出、负债和资金变化。
- 有数据时展示净流量趋势与支出分类构成；趋势图和柱状图在同一张卡片内切换。
- 支持日、周、月、近三个月、近半年和年度等分析跨度；收支复盘还需支持周度、月度、半年和年度切换。
- 图表应在首次进入或切换时平滑绘制，目标动画约 0.8–1 秒；尊重系统减少动态效果设置。
- 图表数字、轴标签、图例要高对比、清晰，尤其柱状图金额不可被裁切或被背景淹没。

### 5.2 收支复盘

- 支出/收入由用户显式切换；按周、月、半年、年查看对应数据。
- 日期摘要卡展示本期总额、相对上一周期变化、日均、笔数、收入、支出、结余、当前总资产。
- 主要金额可做约 0.7 秒数字递增动画，避免一瞬间跳数。
- 月度与年度小结、分类构成、日历每日金额和节奏图表组织在同一复盘体验中；省钱建议嵌在小结里并与事实数据区分，避免为每个小功能额外堆一张卡片。
- 省钱建议结合用户历史收支和资金储备，避免被偶发的一笔大额收入/支出或短期波动误导。算法应有最少观察期、稳健基线/加权思路，并解释建议依据；不得仅凭少量样本给出夸张结论。
- 用户提供的参考图用于理解周/月/年切换、每日金额日历和分类对比，不要求逐像素照抄。

### 5.3 流水、资金、借款、账本

- 流水页面便于按日期回看、筛选支出/收入和定位单笔记录。
- 资金分配页突出五类基础资金及多个计划；流程说明要简短，重复解释性标语应删去。
- 借款与信用页突出剩余总额和简单状态操作。
- 账本管理清楚呈现当前账本、独立账本及撤销/清空操作。

## 6. 视觉与交互规范

- 视觉目标：高完成度的成熟个人财务工具；简洁、有秩序、有温度，避免拥挤、低对比、小字和“为了设计者自己看的标语”。
- “让钱流向生活”可保留；诸如“把测试和生活分开”“按余额管理·不设目标线”等重复解释性文案应删除或改成必要帮助提示。
- 桌面端字体和图表标注要足够大；色彩需顾及对比度，不只依赖颜色表达收入/支出状态。
- 卡片与按钮应有清晰的点击态、hover/focus/pressed 反馈；资金卡片可直接点击，不依赖额外的编辑按钮。
- 常用触控区域目标至少 44px；手机布局不依赖横向滚动才能看到主要标签或关键动作。
- 动效使用轻量、有弹性但不拖慢操作的过渡；加载/图表/数值动画有明确时长，并遵循 `prefers-reduced-motion`。
- 所有看起来能点击的按钮必须有真实功能、明确反馈或禁用状态，不留“空按钮”。

### 移动端专项验收

1. 顶部六个主导航入口同屏可见，不出现横向滑动条。
2. “记一笔”对话框相对当前可视窗口定位；背景页面锁定，弹窗内部需要时才滚动；关闭后恢复原页面滚动位置。
3. 账单预览的确认按钮始终留在预览容器底部；流水列表在按钮上方独立滚动。
4. 对 iOS Safari 动态视口、刘海安全区和 Android 浏览器高度变化有兼容处理。
5. 常用屏宽（320–430 CSS px）没有整体横向溢出，表单字段不被裁切，键盘/短屏下仍可滚动到保存动作。

## 7. PWA、部署与数据安全

- 使用 GitHub Pages 项目子路径 `/solar-flow/`，不改 GitHub 根主页，也不改 Orbit 课表项目。
- 支持浏览器“添加到主屏幕/桌面快捷方式”；Service Worker 缓存应用壳，使离线时可打开和记录。
- 适配 iOS 与 Android 手机、平板及桌面电脑。
- 当前数据保存在浏览器本地。发布只包含程序和静态资源，不包含账本、账单、截图或本机数据。
- 源目录中的需求档案属于本地项目文档，不进入 Vite `dist`，不发布到公网。
- 推荐发布验收闭环：本地单元测试 → 生产构建 → 真实浏览器在桌面/手机视口走查 → 发布静态前端 → 检查公网资源和主要交互。

## 8. 阶段与状态

### 第一阶段（当前核心范围）

- 手动收入/支出记录、总资产基准、虚拟资金及扣减优先级。
- 多账本隔离、撤销/清空、借款与信用基本管理。
- 微信/支付宝等账单表格导入、分类建议、去重、与手动记录匹配、资产影响结算。
- 总览、趋势/柱状图切换、分类构成、日历和复盘小结。
- 响应式离线 PWA 和手机端可用性。

### 后续阶段 / 明确暂缓

- 截图账单 OCR：第二阶段再评估。
- 手机/电脑云同步：用户已恢复该需求并明确“开始”；暂定邮箱 + 密码、验证邮件、找回密码，不使用短信；首次登录需用户明确选择合并本机账本或仅使用云端。Firebase 项目配置和外部发布仍待完成。
- 复杂自动借款匹配：先保证准确；明确匹配自动冲减，不明确的由用户确认。

## 9. 验收基线

- 初始账本为零；手动设置余额后，后续有效流水按日期正确影响总资产。
- 两个来源相同日期的相似交易不会仅因日期相同被合并；真正重复的导入不会重复入账。
- 内部互转不会改变总资产或污染收支统计。
- 一天的流水共用一个日期分组。
- 手机端主导航、记账弹窗、导入确认按钮均可直接发现和操作。
- 图表文字和金额清晰；图表切换/加载不遮挡数据。
- 主要流程的按钮可操作；撤销和清空结果符合账本边界。
- 离线打开与本机数据保存可用；公网仅发布静态代码。

## 10. Prompt 逐轮纪要

以下按本项目对话顺序记录每轮提出的目标、约束和变更。附件中的真实流水内容不复写；只记录附件用途。

1. **寻找 Solar Flow 项目**：先询问是否能找到一个叫 Solar Flow 的旧项目。
2. **更正项目类型**：说明 Solar Flow 指记账软件，不是此前寻找的其他项目；曾怀疑由 Grok 制作。
3. **确立新产品方向**：要求从零制作 Solar Flow，希望它像 Orbit 课表一样可通过 GitHub Pages 发布、添加主屏幕，并离线使用；询问免费多设备同步的可能性。
4. **首轮需求拆解**：要求简洁但有丰富分析（饼图、趋势图、多时间跨度）、手动记录和延迟导入微信/支付宝/银行卡账单；提出同日多账号流水、去重、资产变化和资金类型问题，并要求参考成熟开源项目/交互经验。
5. **产品边界确认**：当前个人使用、未来少量增加；只用人民币；需覆盖欠款/借款/信用卡/分期；提供 GitHub 使用授权；说明无需为个人展示脱敏；引入虚拟资金分配；截图识账延后，首期需实现核心账务与导入。
6. **提供部署参照**：给出 Orbit 的 GitHub Pages 地址，作为推断 GitHub 用户名与项目路径的依据。

- 第一轮实现误把“让现有 Logo 可点击”理解成“新增一个移动版 Logo”，造成顶部出现两个标识。用户指出后已撤回新增标识和齿轮装饰，改为让原有唯一品牌标识本身响应点击。
- 当前实现方向：六个业务入口在手机端等宽、单行、全部可见；设置入口从手机导航行移除并嵌入原品牌点击区域，弹出左侧可滚动设置抽屉，内含账户与同步、数据管理、语言偏好；桌面仍保留侧栏“设置”页面。点击遮罩、关闭按钮或按 Escape 可退出抽屉。
- GitHub 交互参考：采用 shadcn-admin-kit 移动端把侧栏呈现为抽屉的模式，以及 DropDrawer 项目“移动端使用原生抽屉交互、桌面保留直接菜单”的适配思路；未引入其依赖或复制其实现。参考：[shadcn-admin-kit AppSidebar](https://github.com/marmelab/shadcn-admin-kit/blob/main/src/components/admin/app-sidebar.tsx)、[DropDrawer](https://github.com/jiaweing/DropDrawer)。
- 验收：Playwright 390px 与 320px 均只显示一个品牌 Logo，六个业务入口完整在一行；320px 下 document/body 宽度均不超过 viewport；原 Logo 可打开账户、同步、数据管理和语言偏好抽屉，按 Escape 可关闭；桌面侧栏仍可进入“设置”页面。27 项测试、生产构建与 `git diff --check` 全部通过。
- 发布：提交 `59474de`（`Improve mobile navigation and unify settings`）已推送至 `Solar642/solar-flow` 的 `main`。公网首页返回 HTTP 200，最新 HTML 引用 `index-BQv7oDsB.js`，线上 JS 资源返回 HTTP 200，已确认包含原品牌设置入口及统一设置/账户同步内容；提交状态接口未返回单独 CI status 条目。线上部署已通过实际静态资源核验。
