# 数据模型、算法与冲突规则

本文对应当前实现；规则变更时应同步修改测试、README 和用户指南。Solar Flow 是个人记账工具，不是银行账簿或自动对账服务。

## 单一总资产口径

不维护微信、支付宝、银行卡的余额账户。账单来源标签用于识别“从哪个导出来源来”，不会生成账户，也不改变总资产口径。每个账本的资产状态由基准和流水决定：

```text
当前总资产 = 基准总资产
           + 基准日之后计入的收入
           - 基准日之后计入的支出
```

金额以整数“分”运算。`transfer`（明确转账）和 `excluded`（不计收支）方向不参与总资产变化。

### 基准日边界

- `date < 基准日`：只保留作历史统计，不改变当前总资产。
- `date > 基准日`：收入/支出改变当前总资产。
- `date = 基准日`：默认视为已包含在设置的基准余额中。设置基准时会保存时间；之后手工创建且有时间戳的同日流水可以计入。账单行通常只有日期，因此同日导入行按已结算处理。

因此，补算一整天的账单时，把基准日设到首笔待补流水前一天。若某笔当前余额已经包含该日期内的流水，就不要把它当作“未结算”流水再加减。导入前的影响预估会依据此规则计算。

## 多账本和虚拟资金

每个账本各自保存交易、资产基准、资金分配、计划、借款/信用清单和导入批次；新账本初始化为 0，不继承旧账本。登录云同步后，属于同一 UID 的各账本一起同步。

资金分区不是独立账户：

```text
支出顺序：生活 → 其他（未分配余量）→ 自由 → 计划 → 紧急
```

“其他”余额为 `max(0, 总资产 - 所有已分配余额)`。计划余额按计划列表顺序减少。目标线只用于计划金额进度；紧急资金线是动态参考，生活资金不显示目标线。

若真实支出大于当前全部可用分区，系统仍按完整支出金额降低总资产；剩余未覆盖部分不会被忽略或凭空转成收入。

## 账单去重和匹配

匹配按以下优先级逐行处理：

1. **同文件重复流水号：** 来源标签与平台交易流水号相同，后出现行标为重复。
2. **同文件精确重复：** 来源、日期、方向、金额（分）及标准化商户指纹相同。
3. **已导入记录：** 先用“来源标签 + 平台流水号”；若无流水号，再用完整指纹。来源标签按支付导出来源隔离。
4. **手动记录：** 同日期、方向、金额且商户一致/包含关系匹配时，可标为已存在；相差不超过两天且金额方向一致、商户高度相似时，唯一候选会将导入来源信息合并到手动记录。
5. **不确定候选：** 日期/金额接近但商户不同，或存在多个候选，标成待确认；不会静默写入。预览确认按钮不会导入这些待确认行。

### 边界与可能冲突

- 精确指纹包括来源标签，因此更换标签会让同一账单被视为新来源；重复导入同一个导出源时应持续使用同一标签。
- 不同支付平台的导出标签不同，当前不会做全局跨来源交易指纹，也不承诺识别所有跨平台重复项。异源同金额交易可能是两笔真实交易，故不能仅凭日期金额自动合并。
- 两台设备各自手动新建相同内容但不同 ID 的流水不会按商户相似度自动合并；保留两条可避免误删真实交易，但用户需自行检查重复。
- 匹配到唯一手动交易时，优先保留手动交易主体并补充平台流水号、来源文件和原始类型；金额/日期变化按预览中的总资产差额重算。
- 失败、关闭、撤销/作废以及识别为中性/转账的行不计入收入和支出。

## 转账识别

解析器会依据账单方向、交易类型和状态识别收入、支出、转账及排除项。明确写作“转账”或“资金转入转出”的交易类型会成为中性 `transfer`；失败、关闭、撤销等状态会标为 `excluded`。

此机制**不是**跨平台资金配对算法：系统没有账户余额，也不会自动寻找一笔微信转出与一笔支付宝转入并证明它们是同一笔钱。若支付平台将其导出为普通支出和普通收入，两侧都被识别为普通收支时，等额交易只在净资产计算上相抵，收支分类仍会分别显示；只导入一侧或金额不同则会影响余额。导入预览中未显示“内部流转/不计收支”的行应认真核对。

## 分类和人工校正

- 个人保存的商户规则优先，其次是明确商户规则、姓名/商户启发式和平台原始分类，最后才使用“其他/待确认”兜底。
- 餐饮、通信、学校、交通、住房、医疗、订阅等采用关键词规则；学校类商户按当前产品偏好归为“吃喝”。短中文姓名或常见拼写可能被猜测为个人商户并归入“吃喝”，这属于启发式，不保证语义正确。
- 低置信度项目会标记建议确认；导入预览可手动改分类。自动分类不是凭证，名称模糊、同名商户或支付平台泛化字段都可能误判。
- 收入按工资/劳务、退款、人情、投资收益等规则细分；无法判断时保留为其他收入。

## 趋势和资金建议

复盘按本地中国时区的日历日期汇总；趋势序列根据选定周/月/半年/年度范围生成。分类构成不含内部转账和排除项。

### 稳健月基线

现有建议使用最近六个**完整结束月份**，避免把当月未结束数据当成常态。稳健加权函数：

1. 以样本中位数 `m` 和绝对偏差中位数 `MAD` 估计中心与波动。
2. 对单月高值做上界裁剪：`m + 3 × 1.4826 × MAD`；若 `MAD = 0`，上界为 `1.75 × m`。
3. 从较早月份向较新月份作 `alpha = 0.35` 的指数平滑。
4. 最终基线为 `55% × 中位数 + 45% × 指数平滑值`。

紧急资金建议线按最近完整月份必要支出基线乘以 3；必要类别为吃喝、居住、交通、通讯和医疗。如果六个月内没有可用的必要支出分类，则退回总支出。少于 3 个有支出的月份时用中位数并标注初步参考；没有样本时不绘制建议线。它不是硬性目标，不参与支出顺序或强制拦截。

省钱建议至少需要 3 个有记录的完整月份。它比较稳健收入/支出、收入波动、当前总资产与紧急储备，再观察近期可选消费类别是否高于该用户近期基线；样本不足会先提示继续记录。突发收入/支出可能影响趋势，但稳健基线裁剪尖峰，不把单周变化直接当成长期常态。任何建议仅作参考。

## 多设备同步和冲突解决

### 同步范围

每位邮箱验证用户在 `users/{uid}/records` 下保存自己的 profile、账本、交易、借款/信用条目、计划和导入批次。原始 XLSX/CSV/OFX 文件不会发送。解析后的交易/来源元数据会同步（可能包括商户、日期、金额、备注、来源标签、原始分类、文件名和行号）。计划封面 Blob 存在本机 IndexedDB；计划文本/金额等记录同步，实际图片不上传。

### 冲突模型

- 以对象 ID 为键记录更新时间；本机与云端对比后按更新时间较新的**整条记录**获胜，即 last-write-wins。
- 若更新时间完全相同，用稳定的序列化签名作确定性决胜，让两个设备最终收敛；它不是按字段智能合并，也不是 CRDT。
- 不同 ID 的新增交易并存；导入交易使用来源流水号或来源指纹作为同步 ID，重叠导入通常会合并。
- 删除经同步墓碑表示；Firestore 规则不允许物理 delete 请求。
- 连续离线且两台设备修改同一条对象时，较新的版本会覆盖较旧的整条对象。设备系统时间不准确也可能导致“新旧”排序异常。撤销历史仅保存在本机，不作为云端版本回滚。

若需要最保守地处理冲突：等待一台设备显示同步完成后，再在另一设备编辑同一条记录；重要数据先导出；不要在离线时同时改同一条资产基准或计划。
